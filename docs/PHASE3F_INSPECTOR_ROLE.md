## Recommended Neon procedure

Create `drckgomz_inspector` with SQL on the verified development branch, not with the Console/API role-creation flow. Neon documents that Console/API-created roles (and the default Neon CLI role command) receive membership in `neon_superuser`; SQL-created roles do not and instead receive PostgreSQL's ordinary baseline privileges. Neon CLI offers `--access read_only`, but that role is intended to read data; it is too broad for this metadata-only inspection. See [Neon role management](https://neon.com/docs/manage/roles) and its distinction between SQL-created and Console/API-created roles.

The proposed SQL is [create-inspector-role.sql](../../scripts/phase3f/create-inspector-role.sql). It creates a login role without an embedded password, disallows inherited role privileges, database/role creation, replication and RLS bypass, limits concurrent sessions, and grants only `CONNECT` to `neondb`. It grants no schema/table/sequence privileges, no `SELECT`, and no ownership. PostgreSQL system catalogs remain queryable for metadata. No schema `USAGE` is needed for the catalog queries in the prepared preflight.

The SQL cannot prove a Neon branch ID from inside PostgreSQL. Neon documents connections by endpoint hostname, while branch identity is control-plane metadata. Therefore branch scoping is enforced procedurally: immediately before execution, verify in Neon Console that this project, branch ID, and endpoint ID are mapped together; open that exact branch's SQL Editor; confirm its branch selector/URL; and only then execute the script after separate approval. Parsing a connection URL is only one check and is not branch attestation. Do not execute the file through a generic connection or in production. See [Neon branch docs](https://neon.com/docs/manage/branches) on branch endpoints and [Neon role management](https://neon.com/docs/manage/roles) on branch-scoped roles.

Check the branch Roles page first and stop if the role already exists. The `CREATE ROLE` statement will fail if a role with that name appears between the check and execution; the surrounding transaction then rolls back the `GRANT`. Do not replace or reset an existing role blindly. After the reviewed SQL is separately approved and applied in the development branch, set the login password using Neon Console's reset-password flow or `psql`'s interactive `\password drckgomz_inspector` prompt. Do not put a password in the SQL file, shell command, source control, or report. This password-setting step is also a database change and needs to be included in explicit approval.

Neon roles are branch-scoped, and role membership can carry powerful access. Neon documents that roles created in its management interfaces are granted `neon_superuser`, whose memberships include broad data and administrative capabilities. The verification query therefore checks `neon_superuser`, `pg_read_all_data`, and `pg_write_all_data` membership explicitly. Do not grant any of those roles.

## What the inspector can see

- **Schemas, tables, columns, enums, and object names:** yes, via `pg_catalog` metadata. The prepared SQL only reads catalog rows and effective-privilege predicates.
- **Application row contents:** no, if verification confirms no effective `SELECT` privilege on non-system relations and no `pg_read_all_data` membership. The prepared SQL grants neither.
- **Approximate row counts:** it can read `pg_class.reltuples` estimates, which expose only planner metadata. Values can be stale or `-1`/unknown; PostgreSQL documents them as estimates updated by `VACUUM`, `ANALYZE`, and some DDL. The query returns `NULL` for unknown estimates. See [`pg_class.reltuples`](https://www.postgresql.org/docs/18/catalog-pg-class.html).
- **Exact row counts:** not with the no-content-access policy. Exact `COUNT(*)` requires table `SELECT`, and table `SELECT` permits reading records. The inspector must not receive it. This proposal intentionally replaces exact count generation in the general preflight SQL with estimates.

PostgreSQL grants are additive. A grant inherited from `PUBLIC`, a role membership, or an ACL can defeat the intended boundary even when this script grants nothing. The verification now checks all role memberships, role attributes, ownership, effective relation and sequence privileges, callable non-system `SECURITY DEFINER` routines, database/schema CREATE, and explicit default ACL entries to `PUBLIC` or this role for tables, sequences, and functions. Checks use effective privilege predicates, so grants inherited from `PUBLIC` are included. `TEMP` is checked separately because it may be inherited from database defaults; if it is true, stop. Do not revoke shared `PUBLIC` privileges as part of this proposal. Default privileges can change when later migrations run, so repeat verification after any schema change and inspect the migration SQL's default grants before keeping this role active. PostgreSQL's built-in default function EXECUTE behavior is not necessarily represented by a `pg_default_acl` row; continue checking callable `SECURITY DEFINER` routines after later schema changes.

## Verification sequence

After separate approval and creation, configure a second ignored local file with the inspector connection URL. Never replace the existing app URL or use `.env.local`. Before connection, locally confirm its endpoint identifier equals the development endpoint. Then connect only to the development `neondb` with the inspector login and run [verify-inspector-role.sql](../../scripts/phase3f/verify-inspector-role.sql), which starts a read-only transaction and uses a 15-second statement timeout.

Expected results: expected database/role/read-only transaction true; login true; inherit/admin/replication/RLS-bypass flags false; no membership in any role; no ownership of the database or non-system objects; `neon_superuser`, `pg_read_all_data`, and `pg_write_all_data` memberships false; database CONNECT true, CREATE false, and TEMP false; all non-system schema CREATE false; all non-system relation SELECT/write/maintenance privileges false; all non-system sequence privileges false; no callable non-system `SECURITY DEFINER` routines; and no unsafe table/sequence default ACL entries. A failed check means no catalog inventory should proceed.

The verification reports approximate row estimates only. It does not select application table rows or execute `COUNT(*)`. Any later request for exact counts requires a new design and approval because it conflicts with the no-record-access boundary.
